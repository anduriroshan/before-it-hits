Architecture

Google Cloud architecture and four flows

One web app with a selection tool, two Cloud Run services (agents and engine), and a terrain store that makes drawing a box anywhere cheap. Almost nothing is precomputed — the point is that an arbitrary box gets analysed in seconds.

Services

What is staged once vs. computed per box

Staged once — before anyone asks

  • Copy bare-earth terrain tiles into our own storage as cloud-optimised files
  • Fetch the official hazard rasters and record source, date, return periods and licence
  • Fit the modelled population to published ward totals
  • Extract the city's budget lines and capabilities from its documents

Re-hosting terrain is the important one: the public clipping service allows only 50 calls a day for non-academic use, which would fail during judging.

Computed per box — every time you draw

  • Windowed read of just that box, over range requests
  • Reproject and resample onto a 10 m working grid
  • Burn in buildings as walls and roads as shallow trenches
  • Fill depressions, accumulate flow, rank pooling spots
  • Clip the official layer for the matching return period
  • Count who is nearby and rank preparations within the budget

Latency budget for one box

From the published benchmarks. The elevation read dominates — the hydrology is not the bottleneck, which is what makes an interactive selection tool viable at all.

Guard rails, enforced in the architecture

No personal data. Population is modelled from published totals. There is no household register to leak, and messages are drafted for a person to send, never sent by us.
Grounded news is never stored. The licence forbids caching or analysing grounded results, so the display path renders client-side and the storage path uses a separately licensed corpus. Two paths, by design, not by habit.
Nothing derived from map imagery. Depths and terrain come from the elevation store only. We never measure, trace or cache map tiles — which the terms prohibit and which would also be bad science.
